# ADR-015: PROSAIL LUT Inversion via Digital-Twin Engine

## Status

Accepted (2026-04-25, Phase 4 complete: generate_lut + invert with k-NN uncertainty + 6 unit tests)

## Context

v3.1 requires physics-based retrieval of canopy biophysical parameters
(LAI, chlorophyll, leaf water content) from satellite / drone reflectance
using **PROSAIL LUT inversion** (Look-Up-Table inversion of the coupled
PROSPECT-leaf + 4SAIL-canopy radiative transfer model).

v16 already has the forward model:

- `shared/process_models/radiative_transfer.py` — PROSPECT + 4SAIL implementations
- Plus the broader scientific kernel: WOFOST, AquaCrop, APSIM, QUEFTS, SCS-CN,
  Penman-Monteith, soil_carbon, pest_epidemiology, nutrient_management,
  uncertainty, ensemble (`shared/process_models/`)

What is missing:

1. The **inversion path** (LUT generation + nearest-neighbor / Gaussian-weighted retrieval)
2. A **REST/gRPC wrapper** that callers (advisory-service, vegetation-analysis-service,
   yolo26-vision-service) can use without importing the scientific kernel directly
3. **Uncertainty quantification** on retrieved parameters

Phase 1 (row #7) reclassified from 🔴 (new `agronomy-physics-service`) to 🟡
(extend `digital-twin-engine` and reuse `shared/process_models/`).

## Decision

- Add `shared/process_models/prosail_inversion.py` providing:
  - LUT generation (configurable parameter ranges and sampling density)
  - LUT persistence (Parquet on disk + in-memory Faiss / scipy.spatial.cKDTree)
  - Inversion API: `invert(reflectance, geometry, soil_prior) → (params, uncertainty)`
- Expose it via `digital-twin-engine` under `/api/v1/twin/prosail/invert`
  (sync) and `/api/v1/twin/prosail/batch` (async via NATS)
- Cache LUT artifacts in MinIO so they can be regenerated by a scheduled job
  rather than on every container start
- Emit `sahool.twin.prosail.inverted` on completion (tenant-scoped)

No new service.

## Consequences

### Positive

- Physics-grade retrieval available to all consumers via REST
- LUT inversion runs CPU-only; no GPU requirement (unlike yolo26-vision-service)
- Reuses the existing forward model — single implementation, single test suite
- Uncertainty bands propagate downstream into advisory recommendations and
  the explainability layer (`shared/ai/explainability.py`)

### Negative

- LUT memory footprint can be hundreds of MB for high-density grids; mitigated
  by tiered LUTs (coarse / fine) selected by use case
- Inversion is sensitive to view/illumination geometry; callers must pass correct
  geometry metadata (sun zenith, view zenith, relative azimuth)

### Neutral

- New scheduled job for LUT regeneration (monthly by default)
- New env vars: `PROSAIL_LUT_PATH`, `PROSAIL_LUT_DENSITY`

## Alternatives Considered

### Alternative 1: New `agronomy-physics-service`

Rejected — same reasoning as ADR-011 for spatio-temporal: the forward model
already lives next to the twin state and assimilation logic; splitting it off
introduces network hops on what is essentially a deterministic numerical kernel.

### Alternative 2: Pure-ML retrieval (skip physics)

Rejected. v3.1 explicitly requires a physics-grade retrieval path for
explainability and for cases where labeled data is sparse (new crops, new regions).
ML retrieval is complementary, not a replacement, and is already covered by
`yolo26-vision-service` and `crop-intelligence-service`.

### Alternative 3: External library (e.g., `prosail` Python package) called inline

Acceptable as a near-term implementation detail; the in-repo `radiative_transfer.py`
was chosen for vendoring and tenant-scoped reproducibility, but the inversion
module can call into the external package behind a thin adapter if performance
demands it.
