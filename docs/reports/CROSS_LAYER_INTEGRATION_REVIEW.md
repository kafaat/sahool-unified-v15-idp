# Cross-Layer Integration Review Report

**Date**: 2026-03-21
**Scope**: Backend ↔ Middleware ↔ Frontend ↔ Database integration
**Reviewer**: Automated Integration Audit (8 parallel agents)

---

## Executive Summary

A cross-layer integration audit of the SAHOOL platform uncovered **85+ critical integration gaps** where data flows break between layers. The most severe findings include **JWT issuer/audience mismatches causing tokens valid at one layer to be rejected at another**, **RLS policies defined but never enforced** (database tenant isolation is non-functional), **Login response type mismatch** (frontend can't parse backend tokens), and **weather API double-path bug causing 404s**.

## 1. API Contract Mismatches (Frontend ↔ Backend)

### CRITICAL: Login Response Field Names Don't Match

| Field | Frontend (api-client) | Backend (user-service) | Shared Contract |
|-------|----------------------|----------------------|-----------------|
| Token | `token` | `access_token` | `access_token` |
| Expiry | `expiresAt` (string) | `expires_in` (number) | `expires_in` |
| Refresh | `refreshToken` | `refresh_token` | `refresh_token` |

**Impact**: Frontend cannot parse login response. Authentication flow broken.

### CRITICAL: snake_case vs camelCase Across Boundary

- Frontend types use `snake_case`: `farm_id`, `crop_type`, `health_score`, `created_at`
- Backend DTOs use `camelCase`: `farmId`, `cropType`, `healthScore`, `createdAt`
- **No automatic transformation** — 40+ manual mappings in api-client

### CRITICAL: Pagination Response Structure Mismatch

| Frontend | Backend | Contract |
|----------|---------|----------|
| `{ data, total, page, limit, hasMore }` | `{ data, meta: { page, limit, total, totalPages, hasNext, hasPrev } }` | `{ data, pagination: { total, page, limit, hasMore } }` |

All three definitions are different. Frontend can't parse backend pagination.

### HIGH: FieldStatus Enum Drift
- Contract includes `"deleted"` value — backend enum does NOT have it
- `AlertStatus` in api-client missing `"unread"` and `"read"` values from contract

### HIGH: Weather Data Field Names (3 different conventions)
- Frontend: `temperature_c`, `humidity_percent`, `wind_speed_kmh`
- Contract: `temperature`, `humidity`, `windSpeed`
- Backend: varies per service

## 2. JWT Authentication Flow Gaps

### CRITICAL: Issuer Mismatch

| Layer | Expected Issuer |
|-------|----------------|
| Python token generation | `"sahool-idp"` |
| Kong Gateway validation | `"sahool-platform"` |
| Frontend middleware | `"sahool-platform"` |
| Admin middleware | `"sahool-platform"` |

**Impact**: Tokens generated by Python services (`iss: "sahool-idp"`) are **rejected by Kong** and **frontend**.

### CRITICAL: Audience Mismatch

| Layer | Expected Audience |
|-------|------------------|
| Python generation | `"sahool-platform"` |
| Kong validation | `"sahool-api"` |
| Frontend validation | `"sahool-api"` |

**Impact**: Same tokens rejected at gateway level.

### CRITICAL: Tenant ID Claim Name

| Layer | Claim Name |
|-------|-----------|
| Python generation | `tid` |
| Python verification (shared/security) | `tid` (required) |
| Frontend middleware | `tenant_id` (different!) |
| NestJS guard | both `tid` and `tenant_id` |

**Impact**: Token with `tid` claim passes Python but fails frontend validation.

### HIGH: Kong Does NOT Check Token Revocation
- Python backend checks revocation via Redis
- Kong accepts revoked tokens
- Frontend doesn't check revocation
- **Gap**: Revoked tokens accepted at gateway for up to TTL duration

### HIGH: Cookie Name Mismatch
- Web app: `access_token`
- Admin app: `sahool_admin_token`
- No seamless session between web and admin portals

### HIGH: Frontend Auth via Cookies, Kong Expects Header
- Frontend uses httpOnly cookies (no `Authorization` header)
- Kong JWT plugin configured for `Authorization` header
- Potential auth failure at gateway

## 3. Database ↔ Backend ORM Consistency

### CRITICAL: RLS Policies NEVER ACTIVATED
- **File**: `infrastructure/core/postgres/migrations/010_row_level_security.sql`
- RLS policies defined requiring `app.current_tenant` session variable
- **No service calls `SET app.current_tenant` before queries**
- Database-level tenant isolation is completely non-functional

### HIGH: ETag Version Not Incremented on Field Updates
- **File**: `field-management-service/src/fields/fields.service.ts:360-372`
- `update()` doesn't increment `version` field
- `updateBoundary()` does increment version
- **Impact**: Optimistic locking broken for non-boundary updates

### HIGH: user_role Enum Mismatch
- Init SQL: `('super_admin', 'admin', 'manager', 'agronomist', 'field_worker', 'researcher', 'viewer')`
- Prisma schema: `(ADMIN, MANAGER, FARMER, WORKER, VIEWER)`
- Python services using `'agronomist'` will fail on insert

### MEDIUM: Double Connection Pooling
- SQLAlchemy creates pool (20-30 connections) → PgBouncer (250 max)
- Double pooling wastes resources, risks deadlock

### MEDIUM: PostGIS Geometry Not Loaded in findById()
- `Unsupported("geometry")` fields require raw SQL
- `findById()` doesn't execute PostGIS query for geometry data

### MEDIUM: Concurrent Prisma Migration Risk
- Multiple services run `prisma migrate deploy` on startup
- No ordering or locking mechanism for parallel migrations

## 4. Middleware Chain & Data Flow

### CRITICAL: Kong Doesn't Strip X-Tenant-ID Header
- Client can spoof `X-Tenant-ID`
- Backend falls back to header when JWT tenant is missing
- **Attack**: Set `X-Tenant-ID: victim-tenant` without valid JWT

### CRITICAL: No CSRF Validation in Backend
- Frontend generates CSRF tokens and sends `X-CSRF-Token` header
- **No backend middleware validates CSRF tokens**
- No `csrf.py` exists in `shared/middleware/`

### CRITICAL: Middleware Ordering Inconsistent
- FastAPI: last `add_middleware()` = outermost = runs first
- Services register middleware in different orders
- TenantContextMiddleware may run before auth, using header instead of JWT

### HIGH: Kong Headers NOT Forwarded to Backend
- Kong doesn't forward `X-Consumer-ID`, `X-Credential-Username`
- Backend can't identify Kong authentication status

### HIGH: Rate Limiting NOT Tier-Aware at Kong
- Kong: flat 30 req/min for all users
- Backend: tier-based (FREE=30, PRO=60, ENTERPRISE=120)
- Enterprise users hit Kong limit before their tier limit

### HIGH: CORS Headers Duplicated (3 layers)
- Kong adds security headers
- Backend adds same headers via `shared/middleware/security_headers.py`
- Frontend adds same headers in Next.js middleware
- **Duplicate headers may confuse browsers**

### HIGH: Error Response Format Differs Per Layer
| Source | Format |
|--------|--------|
| Kong | `{ error: "string" }` |
| Python rate limiter | `{ error, message, message_ar }` |
| Python SahoolException | `{ success: false, error: { code, message, message_ar } }` |
| NestJS filter | `{ statusCode, message, messageAr, code }` |
| Frontend expects | `{ message, messageAr, code, details }` |

### HIGH: Service-to-Service Calls Rate Limited by Kong
- Internal calls go through Kong
- Kong applies public rate limits
- No service account ACL configured

## 5. Frontend ↔ Backend API Alignment

### CRITICAL: Weather API Double-Path Bug
- Frontend calls: `POST /api/v1/weather/weather/current`
- Kong strips `/api/v1/weather`, leaving `/weather/current`
- Backend expects: `/weather/current` not `/weather/weather/current`
- **Result: 404 Not Found** for all weather API calls
- Test file tests the BUG as expected behavior

### CRITICAL: WebSocket NO JWT Authentication
- `apps/web/src/lib/ws/index.ts:85`
- WebSocket connects without sending JWT token in handshake
- ws-gateway receives unauthenticated connections
- **Any actor can connect to WebSocket and receive real-time events**

### HIGH: Next.js Rewrite Environment Variable Precedence
- `NEXT_PUBLIC_API_URL` (build-time) overrides `API_GATEWAY_URL` (runtime)
- Docker images baked with wrong URL cause silent failures

### HIGH: No Automatic snake_case→camelCase Conversion
- 40+ manual response mappings in `api-client/src/index.ts`
- Business logic in client (e.g., `confidence * 100`)
- Error-prone, silently fails if backend changes field names

## 6. Error Handling Chain

### CRITICAL: Database Errors Expose Implementation Details
- `HTTPException(status_code=500, detail=str(e))` sends raw Python errors to frontend
- User sees: `"TypeError: 'NoneType' object is not subscriptable"`
- Should see: bilingual SahoolException with error code

### CRITICAL: Pydantic Validation Errors Not Bilingual
- Backend: `"body -> area_ha -> greater_than"` (English only)
- Frontend: generic `message_ar: "خطأ في التحقق"` (not field-specific)
- User can't understand which field failed validation

### HIGH: Request ID Lost in Exception Paths
- Request ID middleware sets `request.state.request_id`
- Some exception handlers don't retrieve it
- Frontend error logs lack request ID for debugging

### HIGH: Error Logging Rate Limited (10/min)
- Frontend `/api/log-error` allows only 10 errors/minute
- If app crashes repeatedly, errors 11+ silently dropped
- No circuit breaker or fallback

### MEDIUM: Rate Limit 429 Format Inconsistent
- Kong: standard 429 with headers
- Python: 429 with message but no `message_ar`
- NestJS: default Throttler 429 (not bilingual)
- Frontend can't reliably display bilingual rate limit messages

## 7. Tenant Isolation Across Layers

### CRITICAL: RLS Policies Defined But Never Enforced
- Session variable `app.current_tenant` never set
- All queries return data from ALL tenants
- Complete database-level breach possible with compromised DB credentials

### CRITICAL: LAI Service Allows Tenant Override via Query Parameter
- `GET /api/v1/lai/stress-detection/field-123?tenantId=victim-tenant`
- Valid JWT from any tenant can access any other tenant's data
- Also via `X-Tenant-ID` header override

### HIGH: Events Use Non-Tenant-Scoped Subjects
- Advisory service subscribes to `sahool.*.alert.*` (all tenants)
- Most services use `sahool.field.created` (no tenant scoping)
- Cross-tenant event leakage possible

### HIGH: Kong Does NOT Validate Tenant
- No plugin extracts `tid` from JWT
- No validation of `X-Tenant-ID` header
- No tenant-scoped rate limiting

### HIGH: Admin Cross-Tenant Access Unlimited
- No rate limiting per admin for cross-tenant requests
- No purpose/justification required
- Audit logging exists but no alerting
