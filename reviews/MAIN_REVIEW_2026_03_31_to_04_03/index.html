    مراجعة فرع main — 31 مارس إلى 3 أبريل 2026¶

    المراجع: Claude Code Review التاريخ: 2026-04-03 النطاق: 28 commit, 13 PR, ~130 ملف, +11,962 / -685 سطر

    ملخص تنفيذي¶

    شهدت الأيام الثلاثة الماضية حملة تصليب أمني شاملة عبر المنصة، مع إصلاحات حرجة في عزل المستأجرين، CORS، JWT، وحماية prompt injection. التغييرات ذات جودة عالية بشكل عام مع اختبارات مرفقة، لكن هناك عدة ملاحظات تحتاج متابعة.

    1. إصلاحات الأمان — تقييم: جيد جداً¶

    PR #1445 — إصلاح CORS wildcard¶

    ما تم: استبدال os.getenv("CORS_ORIGINS", "*") بتكوين مشترك عبر shared/cors_config.py في 7 خدمات.

    ملاحظات إيجابية: - allow_credentials يُعطّل تلقائياً عند استخدام wildcard — صحيح أمنياً - Fallback ذكي عبر try/except ImportError يحافظ على التوافق

    ملاحظات سلبية: - [ ] ISSUE-1: الـ fallback في ai-chat-assistant/src/main.py يستخدم CORS_ORIGINS="" (سلسلة فارغة) كـ default بدلاً من "*". هذا أفضل أمنياً لكنه breaking change صامت — خدمة بدون CORS_ORIGINS ستمنع كل الطلبات - [ ] ISSUE-2: الـ allow_headers في الـ fallback يتضمن X-User-ID — يجب التأكد أن هذا الهيدر لا يُستخدم لتجاوز المصادقة

    PR #1435 — سد 13 ثغرة أمنية في خدمات AI¶

    ما تم: إضافة 5 middleware مفقودة (SecurityHeaders, Observability, InputSanitization, TokenRevocation, RateLimit) لـ copilot-api و llm-orchestrator و advisory-service. تعزيز prompt injection detection بـ 7 أنماط عربية جديدة وأنماط jailbreak.

    ملاحظات إيجابية: - أنماط الحماية العربية ممتازة وتشمل: تجاهل التعليمات, تصرف ك, أنت الآن, تظاهر أنك - إضافة فئة jailbreak_patterns منفصلة (DAN mode, developer mode, bypass) - 927 سطر اختبارات في test_ai_middleware_security_gaps.py - كل middleware محاط بـ try/except ImportError لمنع فشل الخدمة إذا لم تتوفر التبعية

    ملاحظات سلبية: - [ ] ISSUE-3: أنماط prompt injection العربية مثل تصرف\s+ك قصيرة جداً وقد تولد false positives في نصوص عادية (مثل "تصرف كمزارع محترف" في سياق تعليمي) - [ ] ISSUE-4: copilot-api/src/main.py يضيف middleware بترتيب قد يكون مشكلاً — TenantContextMiddleware يأتي قبل TokenRevocationMiddleware. إذا تم إلغاء التوكن، يمكن لـ tenant context أن يُهيّأ قبل رفض الطلب

    PR #1446 — user-service: 6 أخطاء أمنية¶

    ما تم: إصلاحات في NestJS user-service تشمل: 1. تغيير UnauthorizedException → ConflictException عند تسجيل بريد مكرر (كان يكشف وجود الحساب عبر 401 بدلاً من 409) 2. إخفاء رسائل الخطأ الداخلية في HttpExceptionFilter 3. إصلاح race condition في incrementOtpAttempts — الآن يستخدم INCR return value بدلاً من EXISTS + INCR 4. إضافة select لـ deactivateUser لمنع تسريب بيانات Prisma

    ملاحظات إيجابية: - إصلاح OTP race condition ممتاز — newCount === 1 أذكى من EXISTS check - التعليق يعترف بعدم atomicity بين INCR و EXPIRE ويقترح Lua script كحل

    ملاحظات سلبية: - [ ] ISSUE-5: تغيير UnauthorizedException → ConflictException (409) عند "Email already registered" يكشف وجود البريد (user enumeration). الأفضل أمنياً هو إرجاع 200 مع رسالة "If this email exists, a verification link was sent" — لكن هذا يعتمد على متطلبات UX

    PR #1449 — Redis TTL وKyverno¶

    ما تم: إضافة TTL (30 يوم) لمفاتيح إلغاء التوكنات في Redis، وإصلاح Kyverno image registry policy.

    ملاحظات إيجابية: - TTL = MAX_REFRESH_TOKEN_DAYS * 86400 — منطقي لأن المفتاح يجب أن يعيش أطول من أي توكن صادر - إضافة logging عند فشل clear_user_revocation وrevoke_token وrevoke_user_tokens - fail-closed pattern: فشل Redis يُعامل كـ "token is revoked" (أمان أفضل)

    ملاحظات سلبية: - [ ] ISSUE-6: _MAX_REFRESH_TOKEN_DAYS يُقرأ من env var عند تحميل الوحدة (module level). إذا تغيرت القيمة في Runtime (مثلاً عبر Vault rotation)، لن تُحدّث

    2. إصلاحات الخدمات — تقييم: جيد¶

    PR #1450 — إصلاح انهيار LLM streaming¶

    ما تم: 1. ollama.py: إضافة try/except json.JSONDecodeError حول json.loads(line) في generate_stream و chat_stream 2. router.py: استبدال cache دائم للـ provider availability بـ TTL 30 ثانية

    ملاحظات إيجابية: - 902 سطر اختبارات جديدة تغطي JSON malformed, TTL expiry, failover chain - استخدام time.monotonic() بدلاً من time.time() لدقة TTL — ممارسة ممتازة

    ملاحظات سلبية: - [ ] ISSUE-7: _AVAILABILITY_CACHE_TTL = 30.0 ثابت في الكود. تحت ضغط عالي، 30 ثانية تعني health check كل 30 ثانية لكل provider — يفضل جعله قابل للتكوين عبر env var

    PR #1448 — notification-service: 10 أخطاء¶

    ما تم: إصلاحات شاملة تشمل: 1. firebase-admin v7 API break: send_multicast() → send_each_for_multicast() 2. تشغيل Firebase SDK في thread pool عبر asyncio.to_thread() 3. إصلاح double-escaping في HTML emails 4. إضافة فحص authorization في update_preferences 5. إضافة null checks لنتائج create_notification 6. FCM data payload يحوّل كل القيم إلى string

    ملاحظات إيجابية: - Backward-compatible fallback: getattr(messaging, "send_each_for_multicast", None) or messaging.send_multicast - asyncio.to_thread() لمنع حظر event loop من Firebase sync SDK - فحص str(user.id) != farmer_id في preferences — يمنع التلاعب بتفضيلات مستخدم آخر

    ملاحظات سلبية: - [ ] ISSUE-8: html.unescape() ثم html.escape() في بناء email templates — هذا النمط غير واضح. إذا كانت البيانات مُطهّرة عند الإنشاء، لماذا يتم unescape ثم escape مرة أخرى؟ يحتاج تعليق أوضح - [ ] ISSUE-9: asyncio.to_thread(firebase_client.send_notification, ...) — لكن send_notification يستدعي messaging.send() الذي قد يكون async في إصدارات أحدث من Firebase Admin

    PR #1447 — weather-service: 6 أخطاء¶

    ما تم: 1. إصلاح race condition في get_publisher() عبر asyncio.Lock() 2. تحسين input validation في request models (min_length, max_length, upper bounds) 3. إصلاح result.get("suitable", True) → result.get("is_suitable", True) (اسم الحقل الصحيح) 4. إصلاح المنفذ في README (8108 → 8092)

    ملاحظات إيجابية: - _publisher_lock = asyncio.Lock() على مستوى الوحدة — يمنع إنشاء عدة اتصالات NATS متزامنة - إضافة wind_speed_kmh: float = Field(ge=0, le=400) — حدود معقولة

    ملاحظات سلبية: - [ ] ISSUE-10: _publisher_lock = asyncio.Lock() على مستوى الوحدة قد يسبب مشاكل مع uvicorn --workers > 1 لأن كل worker سيكون له lock منفصل. هذا مقبول لأن كل worker يحتاج اتصال NATS خاص به، لكن يجب التوثيق

    PR #1442 — إصلاح security middleware وAI guardrails¶

    ما تم: إضافة KeywordSimilarityProvider كبديل offline للتشابه الدلالي مع دعم مصطلحات زراعية عربية/إنجليزية.

    ملاحظات إيجابية: - Jaccard similarity مع agriculture term boosting — بسيط وفعال للبيئات بدون GPU

    ملاحظات إيجابية: - verify_tenant_isolation() توسّع ليشمل جداول billing و audit - Audit middleware يكتب في background عبر asyncio.create_task() لعدم حظر الاستجابة - تنظيف GUCs بعد كل عملية audit write
