    PostgreSQL WAL Archiving to S3/MinIO - Implementation Summary¶

    Overview¶

    Successfully configured PostgreSQL WAL (Write-Ahead Log) archiving to S3/MinIO for disaster recovery and point-in-time recovery (PITR). This implementation provides continuous archiving of database changes to durable object storage.

    Changes Made¶

    1. PostgreSQL Configuration¶

    File: /config/postgres/postgresql.conf (lines 78-116)

    Changes:

    • Updated archive_command from local filesystem to WAL-G script
    • Added comprehensive documentation for WAL-G configuration
    • Configured for S3-compatible storage (MinIO/AWS S3)

    Before:

    archive_mode = on
archive_command = 'test ! -f /var/lib/postgresql/wal_archive/%f && cp %p /var/lib/postgresql/wal_archive/%f'
archive_timeout = 1h

    After:

    archive_mode = on
archive_command = '/usr/local/bin/wal-archive.sh %p %f'
archive_timeout = 1h
# restore_command = '/usr/local/bin/wal-restore.sh %f %p'  # For PITR

    Setup Instructions¶

    Option 1: Docker Compose (Recommended for Development)¶

    1. Update Environment Variables

    bash # Edit .env file WALG_S3_PREFIX=s3://sahool-wal-archive/pg-primary AWS_ENDPOINT=http://minio:9000 AWS_ACCESS_KEY_ID=${MINIO_ROOT_USER} AWS_SECRET_ACCESS_KEY=${MINIO_ROOT_PASSWORD}

    1. Deploy with WAL-G Support

    bash docker-compose -f docker-compose.yml -f docker-compose.walg.yml up -d postgres

    1. Initialize WAL-G

    bash ./config/postgres/scripts/init-walg.sh

    1. Test Setup

    bash ./config/postgres/scripts/test-walg-setup.sh

    1. Create First Backup

    bash docker-compose exec postgres wal-g backup-push /var/lib/postgresql/data

    1. Verify bash docker-compose exec postgres wal-g backup-list

    Option 2: Kubernetes (Recommended for Production)¶

    1. Update Secrets

    bash # Edit k8s-walg-example.yaml # Update S3 credentials in Secret manifest

    1. Apply Configuration

    bash kubectl apply -f config/postgres/k8s-walg-example.yaml

    1. Verify Deployment

    bash kubectl get statefulset postgres-walg -n sahool-database kubectl get pods -n sahool-database

    1. Check Logs bash kubectl logs -f postgres-walg-0 -n sahool-database

    Recovery Procedures¶

    Quick Recovery to Latest State¶

    # 1. Stop PostgreSQL
docker-compose stop postgres

# 2. Clear data directory
docker volume rm sahool-unified-v15-idp_postgres_data

# 3. Restore backup
docker-compose run --rm postgres wal-g backup-fetch /var/lib/postgresql/data LATEST

# 4. Configure recovery
docker-compose run --rm postgres bash -c "cat > /var/lib/postgresql/data/recovery.conf <<EOF
restore_command = '/usr/local/bin/wal-restore.sh %f %p'
recovery_target_timeline = 'latest'
EOF"

# 5. Create recovery signal
docker-compose run --rm postgres touch /var/lib/postgresql/data/recovery.signal

# 6. Start PostgreSQL
docker-compose up -d postgres

# 7. Monitor recovery
docker-compose logs -f postgres

    Point-in-Time Recovery to Specific Timestamp¶

    # Set target time
TARGET_TIME="2026-01-08 14:30:00+00"

# Follow recovery steps above, but use this recovery.conf:
restore_command = '/usr/local/bin/wal-restore.sh %f %p'
recovery_target_time = '${TARGET_TIME}'
recovery_target_action = 'promote'

    For complete recovery procedures, see: /config/postgres/PITR_RECOVERY.md

    Security Considerations¶

    1. S3 Credentials
    2. Store in environment variables or HashiCorp Vault
    3. Never commit to version control

    4. Rotate regularly

    5. Backup Encryption

    6. Enable encryption in transit (TLS/SSL)
    7. Enable encryption at rest (S3 SSE)

    8. Consider client-side encryption with WAL-G

    9. Access Control

    10. Use IAM policies for S3 bucket access
    11. Restrict PostgreSQL container permissions

    12. Enable S3 bucket versioning

    13. Network Security

    14. Use TLS for S3 connections
    15. Implement network policies in Kubernetes
    16. Restrict database access

    Performance Tuning¶

    For Large Databases (>100GB)¶

    WALG_UPLOAD_CONCURRENCY=8
WALG_DOWNLOAD_CONCURRENCY=8
WALG_DELTA_ORIGIN_CONCURRENCY=4
WALG_COMPRESSION_METHOD=lz4  # Faster than brotli

    For High-Write Workloads¶

    # In postgresql.conf
max_wal_size = 8GB
min_wal_size = 2GB
wal_keep_size = 2GB
checkpoint_timeout = 15min

    Troubleshooting¶

    Common Issues¶

    1. WAL Archiving Fails
    2. Check S3 credentials
    3. Verify S3 endpoint accessibility

    4. Review /var/log/postgresql/wal-archive.log

    5. Backup Takes Too Long

    6. Increase concurrency settings
    7. Use faster compression (lz4)

    8. Enable delta backups

    9. Out of Disk Space

    10. Clean up local WAL archive
    11. Adjust retention policies

    12. Monitor storage usage

    13. Recovery Fails

    14. Verify WAL files in S3
    15. Check restore logs
    16. Ensure correct WALG_S3_PREFIX
